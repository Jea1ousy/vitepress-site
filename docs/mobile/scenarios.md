# 13 · 场景设计与面试自测

场景题先澄清约束：用户规模、离线要求、数据一致性、后台寿命和目标设备。下面给出可展开的回答骨架，**不是某个系统唯一正确的架构**。

## 高频业务设计

### 设计一个支持离线、刷新和分页的信息流，怎么回答？ {#feed}

先定义稳定 item ID、排序、游标和分页边界。UI 观察本地数据，网络刷新与追加通过 Repository 协调；数据与游标等元信息应按一致性需求事务化写入。

**追问：刷新与旧分页同时返回怎么办？** 用查询代次、串行协调或事务检查，拒绝把旧查询的追加结果接到新列表。测试重复页、空页、断网、进程重建和账号切换。相关机制见[Paging](./architecture#paging)与[离线优先](./network-storage#offline-first)。

### 搜索输入很快，怎么减少请求并避免旧结果覆盖？ {#search-design}

把输入归一化，按体验设置防抖与去重，用 latest 语义取消旧任务；结果绑定查询 ID 或版本，只有仍有效的结果才能提交 UI。网络库不能可靠取消时，版本校验尤其重要。

空输入、清除按钮、输入法组合文本和失败后继续输入都要明确行为。缓存可以加快重复查询，但 key 要包含筛选、语言与账号等必要维度。

**验证：** 人为让 A 请求晚于 AB 请求返回，确认界面最终仍展示 AB；再让某次请求失败，确认后续输入仍可搜索。[实现思路与代码](./coroutines#search)。

### 断点续传下载如何避免文件损坏？ {#download}

持久化任务 ID、目标 URI、已完成范围与资源验证器；恢复时检查远端资源是否仍是同一表示。Range 请求要验证响应状态、范围与资源版本，不能盲目向旧文件追加。

写临时文件，完成后做长度和业务要求的完整性校验，再原子发布或适当替换；进度更新节流，避免高频数据库写入。系统调度方案根据用户可见性、任务规模、平台规则选择。

**追问：下载百分比到 100% 就完成了吗？** 还可能需要校验、解压和提交。取消、磁盘不足、权限变化、重启与资源变更都要有恢复策略。[标准：范围请求](https://www.rfc-editor.org/rfc/rfc9110.html#section-14)、[后台任务选择](./components#background-choice)。

### 多个请求同时 401，怎么只刷新一次 token？ {#token-refresh}

为同一账号建立刷新协调器：先判断请求使用的 token 是否已过期；若已被其他请求更新，复用新值；否则由单个刷新任务执行，其余等待结果。刷新失败按规则结束会话，避免无限循环。

业务请求最多按策略重放，不能无条件重复非幂等写入；对发送流、上传体等还要确认是否可重新消费。账号切换应使旧刷新结果失效。

**易错点：** 锁只保护状态转换，别让所有业务请求在长时间网络 I/O 内争用同一把阻塞锁。参考[并发控制](./language#locks)和[重试语义](./network-storage#retry)。

## 缓存与算法

### LRU 为什么常用哈希表加双向链表？ {#lru}

哈希表快速定位节点，双向链表支持把已访问节点移动到最近使用端，并淘汰最久未访问项；在常见假设下 get/put 为期望 O(1)，空间 O(capacity)。只有链表查找会慢，只有 Map 又不直接表达访问顺序。

```kotlin
// 演示按条目数限制的单线程 LRU，不是完整生产缓存。
class Lru<K : Any, V : Any>(private val capacity: Int) {
    init { require(capacity > 0) }

    private val entries = object : LinkedHashMap<K, V>(16, 0.75f, true) {
        override fun removeEldestEntry(
            eldest: MutableMap.MutableEntry<K, V>?
        ): Boolean = size > capacity
    }

    operator fun get(key: K): V? = entries[key]
    fun put(key: K, value: V) { entries[key] = value }
}
```

`accessOrder=true` 让访问更新顺序，因此连 get 都可能修改结构；共享时需要协调。图片缓存通常按字节预算，而非只按张数，还要考虑过期、并发请求合并和生命周期。[官方：LinkedHashMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/LinkedHashMap.html)。

### 移动端算法面试优先复习什么？ {#algorithms}

| 类型 | 典型练习 | 需要解释 |
| --- | --- | --- |
| 数组 / 字符串 | 双指针、滑动窗口 | 窗口不变量、重复元素与字符编码边界 |
| 链表 | 反转、环检测、合并 | 空节点、指针更新次序和额外空间 |
| 栈 / 队列 | 括号、单调栈、BFS | 入出顺序与摊还复杂度 |
| 树 / 图 | DFS、层序、依赖拓扑 | 深度、访问标记、环与递归栈 |
| 查找 / 堆 | 二分、Top K | 区间边界、比较规则和复杂度 |
| 动态规划 | 路径、背包、子序列 | 状态定义、转移、初始化和空间优化 |

不要只背代码：二分要说明区间约定，链表要画指针变化，Top K 要比较排序和堆的成本。再把它们连到项目：LRU、任务依赖图、消息去重和列表差异。

**追问：O(1) 就一定快吗？** 实际还受常数、缓存局部性、分配和数据规模影响。先保证正确，再根据实际负载测量。

## 实时、媒体与质量

### 聊天消息怎么实现去重、补拉与最终显示一致？ {#messaging}

客户端生成稳定本地消息 ID，服务端提供可用于去重和同步的标识或序列；持久化发送状态，区分发送中、已确认和失败。断线重连从确认位置补拉，再按协议合并。

**本地发送成功回调、服务端接收确认、对方已读是不同事实。** WebSocket 提供连接上的双向通信，但不能替业务提供端到端持久化、跨重连去重或任意全局顺序保证。

测试断网重发、确认丢失、乱序、重复推送、进程死亡与多设备同步。顺序应由业务协议定义，不用手机墙上时间直接排序所有事件。[标准：WebSocket](https://www.rfc-editor.org/rfc/rfc6455.html)。

### 视频列表如何协调播放、预加载与页面生命周期？ {#video}

明确播放器、可见 item 和宿主的所有权；滚动时只有符合策略的目标播放，复用行时解绑旧 surface 与回调。播放器准备、解码和缓存有成本，不能给每个列表项无限预加载。

页面不可见、音频焦点变化、后台播放、耳机断开和进程恢复要有策略。后台持续播放需用平台允许的媒体与服务机制，不能只让 Activity 的协程继续循环。

**验证：** 快速滚动、切后台、切账号、弱网和反复进出页面，观察同时存活的播放器、内存、首播时间和卡顿率。[官方：Media3](https://developer.android.com/media/media3)。

### 新版本启动慢了，怎么定位并决定停止扩量？ {#regression}

先确认指标定义与样本可比，按版本、设备、系统和实验分组分析，区分全体退化与少数机型长尾。对可复现路径采集 trace，比较新增初始化、资源和依赖变化。

必要时停止扩量或关闭相关开关，同时验证开关是否覆盖启动早期路径。修复后回归启动、内存、ANR 与关键业务，不只看单个时间指标。

**追问：删掉打点后指标变好了算修复吗？** 不算。报告点变化会改变统计口径，应保持可比或明确重建基线。[验证方法](./performance#benchmark)与[发布闭环](./engineering#release)。

### 如何把一个项目讲成可信的技术案例？ {#project-story}

用同一条证据链组织回答：**场景与约束 → 原方案问题 → 观察证据 → 设计取舍 → 实现 → 验证 → 遗留边界**。解释你负责的部分与协作接口，不把整个平台能力都当成自己的实现。

例如“把图片加载从主线程移走”还不够；继续说明解码尺寸、并发上限、缓存预算、页面取消，以及对首屏、P95 帧耗时和峰值内存的影响。没有可复核数据时，坦诚描述定性结论和测量计划，不编造提升比例。
