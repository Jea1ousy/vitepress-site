# 08 · 交互扩展与多智能体

一个智能体的通用程度，取决于它**能观察什么、能作用于什么**。把文本窗口扩展到异步事件、语音、屏幕像素和物理世界，通用性随之上升，工程复杂度也上升。本篇对应《深入理解 AI Agent》第 6、10 章。

## 观察与动作空间决定通用性

书的第 1 章就埋了线索：近年通用智能体的跃迁，来自**合并三类动作空间**——深度研究（网页）、编码（终端与文件）、computer use（图形界面），再把入口延伸到消息渠道与本地文件。**每扩一类观察与动作，就多一片可完成的任务域**，代价是每一类都要自己的护栏与验证方式。

### 异步与事件驱动 {#async-events}

同步对话假设"人等模型"，长任务反过来了：**模型跑几十分钟，人不能守着。** 事件驱动把交互改成任务模型：提交 → 后台执行 → 通知或轮询取结果。

- 任务要有**明确的生命周期状态**（排队、运行、完成、失败），而不是靠聊天记录猜。
- 长任务中间产物**落盘可查**，出错时人能接管现场。
- 远程场景（SSH + tmux 里跑智能体）就是它的手工版——本站 [Codex 远程开发](/codex-remote)记录了具体做法。

### 语音与 Computer Use {#voice-computer-use}

两类扩展走的是同一条权衡曲线——**通用性换可靠性**：

| 模态 | 观察 | 优势 | 代价 |
| --- | --- | --- | --- |
| 语音 | 音频 | 低门槛、免提、实时 | 转写误差、打断处理、时延敏感 |
| Computer Use | 屏幕像素 | 任何有界面的软件都能用 | 每步都比 API 慢且贵，误差逐步累积 |

**像素是最后的选择，不是第一选择。** 有结构化 API 或工具就用工具；computer use 留给"只有界面、没有接口"的软件。误差累积意味着这类智能体必须配检查点与回退策略，不能盲目连跑几十步。

### 多智能体协作什么时候值得？ {#multi-agent}

单个智能体加长上下文能解决多数问题，多智能体的价值在于**隔离与并行**：

- **并行提速：** 任务相互独立时（多文件改造、批量调研），编排者（orchestrator）拆解分派，工作者各自带独立上下文执行。
- **上下文隔离：** 每个子任务的大量中间内容不进主对话——主对话保持干净，只收结论（与[子智能体隔离](./context#compaction)同源）。
- **角色制衡：** 提议者—审查者（proposer–reviewer）模式，让一个模型产出、另一个模型批判，缓解自我确认。

**上下文共享还是隔离，是个真取舍：** 共享省同步成本，但互相污染；隔离干净，但跨任务的依赖要靠拆解质量保证。经验法则：**子任务间无共享状态就隔离，有就明示共享的数据接口**，而不是让它们自由读写同一片上下文。

至于书里展望的"Agent 社会"（智能体间形成分工、交易与协商），当下仍以研究视角看待即可；工程上先让"编排者 + 少量工作者"稳定跑起来。

### 追问：多智能体一定比单个强吗？ {#single-vs-multi}

**不是。** 多智能体引入新的失败模式：拆解错误、结论汇总走样、协调开销指数级上升。书中引用的原则同样适用：**从简单开始，复杂度是成本不是荣誉。** 判断标准很朴素——如果单智能体只是上下文不够用，先试压缩与检索；只有当任务天然可并行、且子任务能独立验收时，多智能体才划算。升级路径永远是：单次调用 → 工作流 → 单智能体 → 多智能体，只在上一层确有瓶颈时进下一层。
