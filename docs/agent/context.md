# 03 · 上下文工程

上下文是智能体最稀缺的资源。窗口再大也有限，注意力随长度被稀释，成本随 token 线性增长。**上下文工程回答的问题是：每一轮，模型应该看到什么？** 本篇对应《深入理解 AI Agent》第 2 章，并与 Missing Semester 智能体编程一讲中的上下文管理实践互相印证。

## 为什么上下文是稀缺资源

三个约束叠加：**窗口上限**（放不下就丢）、**注意力预算**（太长则关键信息被淹没）、**成本**（每轮全量重放历史，见 [ReAct 循环](./core#react)）。所以上下文工程的动作无非三类：省着放（压缩）、按需放（渐进披露）、分开放（隔离）。

### KV Cache 为什么要求前缀稳定 {#kv-cache}

推理分两个阶段：**prefill** 为全部输入 token 计算注意力键值（KV），**decode** 逐 token 生成。前缀相同就能复用已算好的 KV——但**前缀里任何一个 token 变了，它之后的所有缓存全部失效**。

对智能体的直接推论：

- 系统提示不要放时间戳、随机 ID、每次不同的环境信息。
- 动态内容（当前时间、会话 ID）尽量放后缀或独立段落。
- 工具定义在整个会话中保持一致，增删工具等于作废缓存。

**前缀稳定不只是省钱，还是延迟**：缓存命中把每轮的 prefill 从"重算全部"降为"只算增量"。

### 从提示工程到上下文工程 {#prompt-to-context}

提示工程把功夫花在"写好一句话"；上下文工程把功夫花在"设计每轮进入窗口的信息组合"：系统提示、工具定义、历史轨迹、检索内容、技能正文，各占多少预算、按什么顺序排列。措辞仍然重要，但**信息的选择与排布通常比措辞的影响更大**。

### 上下文压缩（compaction）怎么做 {#compaction}

历史增长到接近预算时，常见三招：

- **摘要压缩：** 自动或手动把旧对话摘要成短文本，替换原始历史。摘要会丢细节——精确参数、关键决定、失败路径。**补救办法是让重要状态落盘成文件，摘要里只留指针**，需要时重新读入。
- **倒退对话：** 出现污染（错误方向、注入内容）时回退到较早的状态重来。
- **子智能体隔离：** 把搜索、调研这类产生大量中间内容的任务交给子智能体，主对话只收结论。隔离既省预算，也避免噪声干扰主任务。

### Skills 与渐进式披露 {#skills-progressive-disclosure}

技能（Skill）是"按需加载的说明书"：名称与一两句描述**常驻上下文**，正文只有命中任务时才载入。这把"领域知识全塞系统提示"变成了"目录常驻、正文按需"，是渐进式披露（progressive disclosure）的典型实现。

| 手段 | 进入上下文的时机 | 适合内容 | 代价 |
| --- | --- | --- | --- |
| 系统提示 | 每轮常驻 | 角色、硬约束、输出格式 | 挤占全部预算 |
| `AGENTS.md` / `CLAUDE.md` | 会话建立时载入 | 项目约定、命令、风格 | 过长会稀释注意力 |
| Skill 正文 | 命中任务时加载 | 领域流程、操作手册 | 目录项仍占少量预算 |
| 子智能体 | 只回传结论 | 搜索、调研等高噪声任务 | 派发与汇总有损耗 |
| 检索（RAG） | 命中查询时注入 | 领域知识、文档 | 召回质量决定上限 |

### 项目约定文件怎么写 {#agents-md}

`AGENTS.md` 是智能体进入项目时预读的说明书。写得有效的共同点：**短、可执行、只写模型默认会做错的事**——构建与测试命令、代码风格红线、目录结构约定、常见陷阱。写成"新人入职文档"而不是"愿望清单"。本站 [Codex 工作流](/codex-workflow)里的项目规则就是这个用法。

### 追问：窗口越来越大，还需要管理上下文吗？ {#long-context}

**需要。** 窗口扩大解决"放不下"，解决不了"看不清"和"太贵"：注意力稀释随长度变差，全量重放的成本随长度线性上涨，KV Cache 的显存占用更是涨得比窗口快。长窗口是上下文工程的兜底，不是替代品。
