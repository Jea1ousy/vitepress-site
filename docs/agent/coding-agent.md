# 06 · Coding Agent 与通用 Agent

所有智能体形态里，coding agent 最先成熟、也最接近通用。本篇对应《深入理解 AI Agent》第 5 章；上一篇讲怎么**用好**（[工具基座与智能体编程](./tools)），这一篇讲怎么**造**。

## 为什么代码是"能创造新工具的工具"

书里给 coding agent 的定位是：**代码是能创造新工具的工具。** 两层原因：

1. **通用性：** 只要能写代码并执行，任何可编程的能力都能现场造出来——解析一种新格式、调一个没有现成 MCP server 的 API、批处理一千个文件。工具库不用穷举，组合发生在代码里。
2. **可验证性：** 代码天然带着反馈回路——编译、类型检查、测试、运行输出。**能不能自动验证，直接决定智能体能不能自我迭代**，这让 coding 成为闭环最完整的智能体场景。

### 反馈回路决定迭代质量 {#feedback-loops}

**智能体的自我修正上限，等于反馈信号的质量上限。** 同一个任务，只给"编译不过"它能改语法；给上类型检查它能修类型；给上失败的测试用例它能逼近行为正确。测试驱动开发（TDD）之所以与智能体特别契合，是因为**测试就是可执行的验收标准**——先让需求变成断言，剩下的迭代可以交给循环。

信号优先级从高到低：**失败的测试 > 类型检查 > lint > 人工 review。** 越靠前越便宜、越客观，能自动化验证的绝不留给人眼。

### 并行智能体与工作区隔离 {#parallel-worktrees}

多个智能体并行开工时，核心问题是**修改冲突**：大家改同一个工作区，互相覆盖。`git worktree` 给每个任务一个独立检出目录，各跑各的分支，完成后按常规流程合并与测试。隔离解决冲突，**不解决正确性**——合并前的验证和 review 仍然由人负责。

### 通用 Agent 与 coding agent 的关系 {#general-agent}

浏览器操作、文档问答、数据分析……这些通用场景走两条路线：给专用工具（结构化、可靠、维护重），或者**统一降到代码执行**（通用、表达力强，需要沙盒兜底）。趋势是后者承担越来越多：工具即代码、技能即代码、评估即代码。**掌握 coding agent 的构造，等于掌握了大多数智能体的骨架。**

### 追问：关键代码应该手写吗？ {#handwrite-critical}

**验证成本高于编写成本的代码，值得手写。** 安全敏感逻辑（鉴权、加密、支付）、并发核心、错误处理路径——这些地方错误藏得深、测试难覆盖，智能体"看起来能跑"最危险。日常 CRUD、胶水代码、样板改造则放手交给循环。书里的提醒值得贴在工位上：**审查有时比编写更难，人保留判断，智能体负责产量。**
