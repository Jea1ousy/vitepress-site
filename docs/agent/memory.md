# 04 · 记忆与知识库

会话结束，上下文就消失。智能体要在更长的时间里变得可靠，需要两类持久化：**关于这个用户的记忆**和**关于领域的知识库**。本篇对应《深入理解 AI Agent》第 3 章，也是 [学习的三个时间尺度](./core#learning-timescales) 中"持久化外部产物"的主战场。

## 三种"记住"，先分清

| 概念 | 存什么 | 生命周期 | 典型载体 |
| --- | --- | --- | --- |
| 上下文 | 本轮对话的一切 | 单次会话 | 对话历史、工具结果 |
| 用户记忆 | 偏好、事实、进行中的事 | 跨会话，按用户 | 记忆库、画像 |
| 知识库 | 领域知识、文档 | 独立于用户 | 向量库、索引、图谱 |

**记忆解决"它认识我"，知识库解决"它懂业务"。** 两者都通过检索进入上下文，但写入方、更新频率和隐私边界完全不同。

### 用户记忆和 RAG 有什么不同？ {#memory-vs-rag}

- **写入方不同：** 记忆多由智能体在交互中主动提取写入（用户说过"我用 pnpm 不用 npm"）；知识库由离线流程构建（文档解析、切分、索引）。
- **更新节奏不同：** 记忆随对话增量更新，需要合并与冲突处理（用户新偏好覆盖旧的）；知识库随语料批量更新。
- **评价标准不同：** 记忆看"个性化是否准确、是否越界"；RAG 看"召回与引用是否可靠"。

两个容易低估的环节：**切分**（按语义边界切，保留标题层级等结构线索，比固定长度好）和**重排**（粗召回靠向量，精排用交叉编码器，性价比很高）。**生成时要求带引用**，既方便人验收，也能压制编造。

### 结构化索引与知识图谱什么时候需要？ {#structured-index}

向量检索擅长"语义相近"，不擅长"精确关系"。两类场景要加结构：

- **元数据过滤：** 按版本、日期、权限先过滤再检索，往往比换更强的嵌入模型有效。
- **关系型问题：** "A 的依赖里谁也依赖了 B"这类多跳问题，图或关系表的表示比文本块直接。

实践中常见"结构化索引打底、向量检索补语义"的混合方案，先让过滤条件生效，再在候选集里做语义排序。

### 记忆怎么写、怎么忘 {#write-forget}

写入要有门槛：**显著事实、明确偏好、可验证**的才值得存。"用户喜欢简洁回答"是偏好，"用户上次说下周再改"是进行中的事——都值得存；一次性的任务细节不值得。

- **合并与冲突：** 新记忆与旧记忆冲突时，通常新的赢，但要留痕而不是静默覆盖。
- **遗忘是能力：** 过期、已解决、被推翻的记忆要能淘汰，否则检索质量被噪声拖垮。
- **隐私是边界：** 记忆含个人数据，需要提供查看、删除与导出；跨用户隔离必须默认生效。

### 追问：长上下文会取代 RAG 吗？ {#long-context-vs-rag}

**不会整体取代。** 知识库的规模通常远超窗口，全量塞入既贵又稀释注意力；RAG 还提供引用、权限控制和按需更新——知识一换，智能体立即"学会"，不必等训练。窗口扩大改变的是**检索单块可以更大、需要压缩的场景变少**，"检索进入上下文"这个骨架不变。

**微调也不能代替 RAG：** 微调改的是参数，适合固化风格与技能（见[评估与持续进化](./eval-evolution)）；高频更新的知识放参数里，更新成本和幻觉风险都不划算。判断标准是知识的变化频率：天级变化走检索，基本不变才考虑进参数。
