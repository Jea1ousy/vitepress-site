# 02 · Agent 核心公式与 Harness 工程

本篇对应[《深入理解 AI Agent：设计原理与工程实践》](https://github.com/bojieli/ai-agent-book)第 1 章。全书围绕一个公式展开，先把公式讲准，后面所有专题都是在回答它的某一项。

## 一个公式看清 Agent

**Agent = LLM + 上下文 + 工具。** LLM 是大脑，负责推理与决策；上下文是眼睛，决定模型这一轮能看到什么；工具是手脚，让模型改变外部世界。公式里没有"环境"，但智能体与环境构成"观察—行动"闭环：环境响应动作，产生新的观察。

生产级形态是 **Agent = 模型 + Harness**。Harness 是智能体边界之内、模型之外的全部工程：上下文管理、工具接口，以及约束（constrain）、验证（verify）、纠错（correct）。**当模型能力商品化，"能做事"到"可靠地做事"的差距主要在 Harness——这是这本书的核心论点。**

### Harness 到底管什么？ {#harness}

一条实用的边界规则：**工具定义和沙盒权限属于 Harness；沙盒内的文件与进程、外部数据库属于环境。** 前者是你设计的接口，后者是你与之交互的世界。

| 问题 | 归属 |
| --- | --- |
| 给模型定义哪些工具、描述怎么写 | Harness |
| 智能体能执行什么命令、读写哪些路径 | Harness（沙盒权限） |
| 沙盒里被改掉的代码文件 | 环境 |
| 外部数据库、第三方 API 的真实状态 | 环境 |

### ReAct 循环与上下文结构 {#react}

主流智能体运行在 ReAct 循环上：推理（Reasoning）、行动（Acting）、观察（Observing）交替，直到完成。上下文由两部分构成：**静态前缀**（系统提示 + 工具定义）加上**不断增长的轨迹**（用户消息、模型回复、工具结果）。

**上下文是只追加（append-only）、每次全量重放的。** 每一轮推理都把全部历史再发一遍。这一性质解释了后面所有成本现象：为什么前缀稳定性重要（[KV Cache](./context#kv-cache)）、为什么历史越长越贵、为什么压缩和隔离能省钱。

### 工程范式在怎么演进？ {#paradigms}

提示工程 → 上下文工程 → Harness 工程 → Loop 工程 → Graph 工程，每一层嵌套在下一层里。模型能力上升会逐步吸收下层的工程，**但速度有限：模型还做不稳的，Harness 先补上。** 在当前能力边界上，Harness 工程依然值钱；等模型稳稳吃掉一层，工程重心就往上移一层。

### 工作流还是自主智能体？ {#orchestration}

| 维度 | 工作流（Workflow） | 自主智能体（Autonomous Agent） |
| --- | --- | --- |
| 步骤 | 预先编排，路径确定 | 模型动态规划 |
| 可预测性 | 高，易测试 | 低，需护栏 |
| 适用 | 流程固定、步骤可枚举 | 开放式任务、路径难以预设 |
| 成本 | 编写成本 | token 与调试成本 |

**从简单开始：单次调用 → 工作流 → 自主智能体，只在确有需要时升级。** Anthropic 的[构建高效智能体](https://www.anthropic.com/research/building-effective-agents)给出三条原则：保持简单、保持透明、设计好智能体与计算机的接口（ACI）。Harness 的复杂度不是美德——"Less structure, more intelligence"。

### 护栏怎么分层？ {#guardrails}

按绕过难度递增分三层，生产系统通常三层并用：

| 层 | 管什么 | 手段 |
| --- | --- | --- |
| 上下文层 | 模型看到什么 | 提示注入防御、输入过滤、来源标记 |
| 执行层 | 模型能做什么 | 工具风险分级、沙盒、人工介入点 |
| 数据层 | 能碰哪些数据 | 行级权限、信任边界、最小授权 |

**人工干预是执行层最硬的一道闸。** 高风险动作（删除、支付、外发）必须有人确认，并把确认点设计得不可跳过。

### 学习的三个时间尺度 {#learning-timescales}

智能体的"学习"发生在三个时间尺度上，后续专题分别展开：

1. **上下文内适应：** 会话内从反馈中调整，会话结束即消失。
2. **持久化外部产物：** 更新文档、提示词、Skills、代码——不重训模型就能积累。
3. **参数更新：** 通过后训练改变模型本身，见[评估与持续进化](./eval-evolution)。

### 追问：模型变强后，Harness 会被淘汰吗？ {#harness-future}

**会被部分吸收，不会整体消失。** 模型每代都在吃掉原来靠 Harness 兜底的场景（比如工具调用格式早已内化），但新的能力边界又会产生新的 Harness 需求。判断标准很实际：**在目标模型上跑评估，哪类失败仍然高频，哪类就仍然需要 Harness。** 书中第 1 章的上下文消融实验是个好例证：删掉工具结果，模型会盲目重试；删掉工具定义，模型会一本正经地编造——这两类失败都不是靠换更强模型解决的。
