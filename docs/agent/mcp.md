# 05 · 工具生态与 MCP

工具是智能体的手脚，也是 Harness 里你最直接可控的部分：工具定义、执行权限、错误返回全由你设计。本篇对应《深入理解 AI Agent》第 4 章。

## 工具的三种类型

书里把工具按用途分三类，分类的用处在于**风险分级和权限设计**可以按类展开：

| 类型 | 干什么 | 例子 | 风险特征 |
| --- | --- | --- | --- |
| 感知 | 读世界 | 搜索、读文件、浏览器、数据库查询 | 泄露上下文，破坏性低 |
| 执行 | 改世界 | shell、代码执行、写入、发布 | 破坏性高，需要沙盒与确认 |
| 协作 | 联系人或别的智能体 | 消息、任务管理、子智能体派发 | 影响面外溢，需限额 |

### 工具定义为什么占用上下文预算 {#tool-defs}

工具列表进入静态前缀，**每个工具的名称、描述、参数 schema 都按 token 计费，且每轮重放**（见 [KV Cache](./context#kv-cache)）。挂五十个工具，还没开始干活预算就去了一小半。所以工具集合要按任务裁剪：给编码智能体挂上日历和外卖，是双输。

**描述是给模型看的 API 文档。** 模型选错工具、传错参数，多数时候是描述含糊。写描述时问自己：一个没见过这个系统的新人，只靠这段话能选对、传对吗？

### MCP 解决什么问题 {#mcp}

没有统一协议时，M 个智能体框架对接 N 个工具服务，要写 M×N 份适配代码。[Model Context Protocol](https://modelcontextprotocol.io)（MCP）把它变成 **M+N**：工具方实现一次 server，智能体方实现一次 client，两边按协议见面。

要点：

- **架构：** host（智能体应用）内嵌 client，与一个或多个 server 通信；底层是 JSON-RPC。
- **原语：** server 可以暴露 tools（模型可调用的动作）、resources（可读取的数据）、prompts（可复用的提示模板）。
- **效果：** Notion、GitHub、数据库等服务有了现成 server，智能体"即插即用"。Missing Semester 智能体编程一讲里演示的 Notion server 就是典型用法。

**MCP 管的是"怎么接"，不管"该不该"：** 鉴权、配额、风险分级仍在 Harness 里做。接了一个能删库的 server，协议不会替你拦住它。

### 主动工具发现 {#tool-discovery}

工具多到没法全量常驻时，让模型按需发现：常驻的只有一份工具目录的摘要，模型先查目录、再加载具体工具定义——和 [Skills 的渐进披露](./context#skills-progressive-disclosure)同一个思路，只是作用在工具上。

### 好的工具接口长什么样 {#tool-design}

Anthropic 的建议是**防呆（poka-yoke）思维**——把容易犯的错从接口上排除：

- **参数少而正交：** 能从环境推断的（工作目录、当前时间）不做成参数。
- **返回面向模型：** 错误信息要可读、可行动——"权限拒绝，尝试 X"比异常堆栈有用得多。
- **粒度匹配任务：** 太碎则模型被迫多轮组装，太粗则出错时难以定位与回滚。
- **最小权限：** 每个 server、每个工具只授予完成任务必需的范围。

### 追问：工具越多越好吗？ {#too-many-tools}

**不是。** 工具越多，选型错误率越高、前缀预算越大、测试面越宽。更好的路径通常是：先给模型**代码执行 + 一组底层原语**，让组合发生在代码里——这也是 coding agent 成为通用能力入口的原因之一，见[下一篇](./coding-agent)。
